# CAG stress test — report

Where does the conversational estimator (CAG: metadata + summary + anchors + sliding window, everything re-injected every turn) start to break?

## Run

| Parameter | Value |
|---|---|
| Model | `gpt-4o-mini` (estimation, metadata extractor and summarizer) |
| Scenarios | growing, pivot, contradiction (20 turns each) |
| Attachment (KB of extracted text) | 0, 20, 100 (100 KB is truncated to `MAX_ATTACHMENT_CHARS = 60 000`) |
| Repeats per cell | 1 (reduced run; the exercise's full run uses 0,5,20,50,100 × 3) |
| Window | `MAX_CONVERSATION_TURNS = 6` pairs; heuristic anchors |
| Budgets | latency 8 000 ms/turn · cost 0.02 USD/turn |
| Tracked fact | the turn-1 project name (Nimbus / Helios / Atlas) in `metadata.project_name` |

```powershell
uv run python -m evals.stress.run --http http://localhost:8000 --scenarios growing,pivot,contradiction --attachment-sizes 0,20,100 --repeats 1 --output evals/stress/results.csv
uv run python -m evals.stress.report --csv evals/stress/results.csv --write evals/stress/REPORT.md
```

How to read the columns:

- `latency_ms` is the main LLM call (validation re-prompts included), not the HTTP round-trip. `wall_clock_ms` in the CSV adds guardrails, extraction, compression and the metadata extractor.
- **Cache hit %** is 0 by design: the conversational path does not use the exact or semantic cache (every turn depends on the history), and `cache_hit_kind` is always `none`.
- **Recall** = `MemoryDriftMetric` passes from turn 2 onwards (turn 1 always remembers itself and is left blank).

## Reading

**Where does it break, and which dimension dominates?** The **latency** budget breaks first and on every profile. With no attachment, the median `latency_ms` is already 7.4 s at turn 2 and 16 s at turn 5, as the window fills up (table 2d). Only 8 of the 119 OK turns came in under 8 s, all of them in the first turns of the 0 KB sessions. Table 2a shows the mechanism: latency grows monotonically with `tokens_in`, and 91 of 119 turns go over 20 000 input tokens. **Cost** only breaks when there is an attachment. At 0 KB the full 20-turn session costs 0.068 USD and no turn exceeds 0.02 USD. At 100 KB the budget fails from turn 3–5 (growing 3, pivot 4, contradiction 5) and 33 of 49 turns go over it. Pivot 100 KB accumulates 0.557 USD over 20 turns, 8× the 0.068 USD of growing 0 KB. **Memory does not degrade**: recall of the turn-1 project name is 100 % across all 119 turns, including turns 7–20 when the turn that introduced it had already left the window. It survives through `metadata.project_name` and the cumulative summary, even with `anchors_count = 0` throughout. The **real break**, not covered by the three budgets, is robustness: **6 of 9 sessions aborted** with a 502 (turns 3, 8, 10, 13, 13, 18). In every case the arithmetic validator rejected the answer because the summary's total did not match the sum of the phases, and 3 re-prompts did not fix it. It does not depend on attachment size: two of the aborts are at 0 KB, one of them at turn 3. But it is cumulative: the longer the session, the more chances to fail, and only 3 of 9 sessions reached turn 20. And each retry re-sends the whole context: in pivot 100 KB, `tokens_in` jumps in multiples of about 81 k (81 k → 162 k → 245 k → 326 k), i.e. 1 to 4 calls per turn. Conclusion: from **turn 2 on latency**, from **turn 3–5 on cost with large attachments**, and from **turn ~8–13 on reliability**. Latency dominates the degradation, and retries amplify both latency and cost.

**What edge case justifies moving to RAG?** A large attachment in a long conversation. The window stores the full rendered `user_message`, attachment included, so with `MAX_CONVERSATION_TURNS = 6` the prompt carries up to six copies of the same document. That is why a single 100 KB call grows from about 40 k tokens at turn 1 to about 81 k once the window is full. Worse, the 100 KB document is truncated to 60 000 characters, so about 40 % of its content is invisible to the model from the very first turn. That is a memory loss `MemoryDriftMetric` does not measure, because it only tracks the project name. The threshold this data supports: **an attachment of ≥ 20 KB that has to be consulted for more than ~5 turns**, or any document above `MAX_ATTACHMENT_CHARS`. Past that point CAG pays O(turns × document) per session. RAG pays O(top-k chunks) per turn, keeps the window holding only the conversation, and reaches the part of the document that truncation cuts off today. For short conversations without attachments CAG is still fine: 0.07 USD and perfect recall over 20 turns. There, the problem is latency and validator retries, not the architecture.

_Limitations:_ 1 repeat per cell, so the P95 values come from 2–20 points. The tracked fact is the easiest one to remember, because the extractor stores it in a structured field. The pivot (React Native → Flutter) and budget (30 000 → 80 000 EUR) facts are not scored. GET `/sessions/{id}` does not expose anchor text, although no anchors were created in this run anyway.

## Methodology decisions

- **Metrics in `evals/stress/metrics.py`, not in `evals/metrics.py`.** Those in `evals/metrics.py` evaluate `(GoldenCase, EstimationResult)`, i.e. the quality of one estimate. These evaluate a `TurnObservation` (latency, cost) and the session snapshot (memory). Different signature, same `MetricResult`.
- **Telemetry in the POST response**, not by parsing `docker compose logs`. It reaches the runner together with the result and works both via HTTP and in-process. The `turn_observed` event is still emitted with the same content.
- **Real `turn_index`.** It used to be computed as `len(window) // 2` and got stuck at 7. Now it comes from a `Session.turn_count` counter.
